# RAG 评测规格（判定逻辑）

> 实现：`scripts/eval.mjs`　数据：`eval/golden.jsonl`　报告：`eval/reports/*.json`
>
> 原则：**能规则的不用模型判，能分档的不报总分。**
> 生成层用的 prompt 与线上同一份（`src/lib/rag/prompt.js`），否则测的不是线上那套。

---

## 一、golden set 格式

```jsonl
{"id":"q001","tier":"easy","question":"...",
 "gold":[{"documentId":"","quote":"语料里的原文片段"}],
 "must_contain":["23"], "must_not_contain":[],
 "should_refuse":false}
```

| 字段 | 作用 | 约束 |
|---|---|---|
| `tier` | `easy` / `hard` / `unanswerable` | 三档分开算指标，整体数字会掩盖问题 |
| `gold[].quote` | **原文引文**，不是 chunkId | 改分块/换 embedding 后不用重标 |
| `must_contain` | 必须精确出现的数字/实体 | 只放能机器比对的，别放整句 |
| `should_refuse` | 是否必须拒答 | `unanswerable` 档为 true |

**导入格式**（CSV 表头固定，JSONL 字段同名）：

```csv
question,tier,gold_quotes,must_contain,should_refuse
"业务设备里 data_type=3 代表什么？",easy,"3 具体服务器（有 device_ip）",服务器,false
"这个系统的日活用户数是多少？",unanswerable,,,true
```

- `gold_quotes` / `must_contain` 用 `|` 分隔多条
- `tier` 留空时自动推断（`should_refuse=true` → unanswerable，否则 easy）
- 缺 `question` 的行会被跳过并在返回里报出来

## 二、四项指标与判定

### ① 检索命中（完全自动）

```
命中判定：overlap(召回块, gold.quote) ≥ 0.6
overlap  = quote 的字符二元组中，出现在块里的比例（去空白/标点后）
Hit@K    = topK 内至少命中一条 gold
Recall   = 命中的 gold 数 / gold 总数
```

阈值 0.6 是经验值：太低会把「同主题不同段」判成命中，太高会被分块边界切断。

### ② 引用正确率（断言级，规则优先）

```
1. 按 。！？；\n 切句
2. 抽取 [citation:N]
3. 引用继承：没有引用的句子，若后面 3 句内出现引用，继承那一个
   （模型常写成「一句话 + 一串列表 + 末尾一个 citation」，不继承会冤枉它）
4. 对每个被引用的块判「是否支撑该断言」：
     数字全等（断言里的数字必须在块里精确出现）        ← 硬规则
     且 支撑度 = max(词面覆盖率, 最长公共子串占比) ≥ 0.35
   两条都过 → 支撑
引用正确率 = 判为支撑的引用数 / 总引用数
无引用断言率 = 有事实断言（含数字或长度 > 15）却没带 [citation:N] 的句子占比
```

支撑度取两种覆盖率的较大者，是因为断言里常混着问题措辞（「业务设备里 data_type=3 代表…」），
纯 bigram 覆盖率会被稀释到 0.4 以下，把正确引用误判成不支持。

数字规则排第一，是因为**数字错配是最难辩解、也最容易自动判的幻觉**。

### ③ 幻觉率

本实现报 **H1 无支撑率** = 未被任何 cited 块支撑的断言 / 总断言数。

**不参与统计的情况**（否则指标会被污染）：
- 拒答的回答：本来就不该有引用，算成「无支撑」是冤枉
- 空回答：没有断言可判，单独用 `empty` 计数（本地小模型跑满 token 时会出现）
- `should_refuse` 档整体：只报拒答率

⚠️ 不要用「回答 vs 标准答案的相似度」当幻觉率——那是正确率。

### ④ 拒答

```
模型拒答 = 命中拒答模式 且 没有给出带引用的实质答案
拒答模式 = 没有|未提及|未包含|无法|找不到|文档中没|not mentioned|no information|cannot find

拒答率（unanswerable 档）= 正确拒答数 / unanswerable 总数
误拒率（answerable 档）  = 应当作答却拒答的比例
```

### ⑤ P0 级错误（硬门禁）

```
该拒未拒   （should_refuse=true 但给了带引用的具体答案）
数值错配   （断言里的数字在引用块中找不到）
```

P0 不为 0 就不该上线——它直接对应「客户敢不敢用」。

## 三、跑法

两种入口，同一份内核（`src/lib/rag/eval.js`）：

**页面**：知识库详情页 → 「质量报告」卡
- 「运行评测」：只跑检索层，2 秒返回
- 「导入测试集」：上传 CSV / JSONL，**按知识库存储**，立刻生效（CLI 也会优先用它）
- 「模板」：下载 CSV 模板
- 「清空」：回落到内置示例 `eval/golden.jsonl`
只跑检索层（命中率/Recall），2 秒返回；生成层指标需跑 CLI，页面会显示最新一份报告。

**CLI**：可以跑全链路，适合放进 CI / 回归。

```bash
node scripts/eval.mjs --retrieval-only     # 只算检索层，几秒
node scripts/eval.mjs                      # 全链路（含生成，慢）
node scripts/eval.mjs --limit 3            # 调试
node scripts/eval.mjs --tier unanswerable  # 只跑某一档
node scripts/eval.mjs --kb kb_xxx --user user_xxx
```

输出（本机实测，8 条样本）：

```
档位          样本  命中@K  Recall  引用正确 幻觉H1  拒答率  误拒率  P0
easy          4     100.0%  100.0%  100.0%  0.0%    —      0.0%    0
hard          2     100.0%  100.0%  50.0%   50.0%   —      0.0%    0
unanswerable  2     —       —       —       —      100.0%  —       0

失败样本
  · [q003] 策略应该按什么键查？  原因：空回答
```

这三行数字本身就是结论：**检索没问题、拒答没问题，问题在生成层的引用覆盖**——
「四层对象」这种多条目答案只给了 1 个引用，单块撑不住 4 个断言。

## 四、判定器的可信度

任何自动判定都要先自证，否则数字不能拿去汇报：

1. 人工先判 20–30 条（逐条标 正确/错误）
2. 跑同一批，算判定器与人工的一致率
3. 一致率 < 85% → 改规则，不要把数字写进 README

汇报时带上**样本量 + 判定方式**：「50 条，检索层规则判定，生成层规则 + 人工抽检 20 条」。

---

## 五、判定器的已知局限（要主动说）

| 局限 | 表现 | 为什么先接受 |
|---|---|---|
| 引用继承 | 一串列表末尾的引用会被前面的条目共享 | 不继承会把正确答案判成高幻觉，宁可松一点 |
| 单引用覆盖多条 | 「四层对象」答对但只引 1 块 → 判不支持 | 这本来就是真实缺陷（引用不足以支撑结论） |
| 语义等价没判 | 换一种说法但意思对，可能判覆盖不足 | 规则判定的代价，靠人工抽检补 |
| 数字存在性而非一致性 | 断言里的数字只要出现在块里就放过 | 精确比对需要上下文对齐，MVP 不做 |

**因此：报数字时必须带「规则判定 + 人工抽检 20 条」**，不要把它说成绝对准确率。

## 六、回归门禁建议

- 任一指标相对基线退步 > 3pt → 不合并
- P0 错误 > 0 → 不合并
- 每次改检索/切分/模型配置，重跑一遍并把前后对比贴进 PR 描述
